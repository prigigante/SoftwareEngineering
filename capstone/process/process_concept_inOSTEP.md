# 프로세스에 대한 이야기

## 1. CPU와 관련한 가상화

### 프로세스란? 
실행중인 프로그램.  
프로그램: 생명성 없는 것. 단순히 디스크에 존재하며, Instruction들의 묶음이고, action을 기다리는 것.
따라서 운영체제가 이것들의 바이트를 가지고 실행시키고, 변화하여 유용하게 변화시킴.  

### 동시에 사용
우리는 여러 프로그램을 동시에 사용하고 싶어함.  
실제로도 특정 시스템은 "겉으로는" 수십에서 수백개의 프로세스들이 "동시에" 동작하는 것으로 보임.  
이렇게 동시에 실행되는것처럼 보인다는 것은 사용자가 별생각 없이 프로그램을 실행하면 하면 되므로  
=> OS를 쉽게 이용가능하게 해준다.  

어떻게 CPU가 많다는 환상을 심을까?  

### CPU가 많다는 환상을 구현하는 방법.  
방법은 바로 "가상화"이다.  

이중. 프로세스 하나를 돌리고, 멈추고, 다시 다른것을 돌리고 멈추고를 반복하는 것.  
이를 통해 CPU가 여러개인 것처럼 흉내낼 수 있다.  (하나 혹은 적어도)  

이러한 기법을 "time sharing" 시분할 방식이라고 한다.  
다만 이러한 기법의 잠재적 대가는 성능이다. 이러한 방식으로  
CPU를 "공유"한다면 개별의 작업은 느리게 실행된다.   

###### Time Sharing  / 시분할
시분할 방식은 가장 기초적이고 기본적인 "자원" 공유 방식이다.  

하나의 엔티티에 아주 약간 자원을 사용하는것을 허용했다가, 다른 엔티티에게 다시 아주 약간 자원을 사용하는것을 허용하는것으로 구현함.  
이러한 방식을 사용하면 요구(CPU 또는 네트워크 링크)받은 자원을 많은 것들에게 "공유" 가능함.  

반대되는 개념은 공간 공유이다. 대개의 디스크공간은 공간분할 방식의 예시임.   
=> 차이점. 시분할과 다르게 "자원" 자체를 나누어(대개 공간) 사용하는 것들에게 "분배"하는 것.

이러한 가상화를 위해서는 저수준 레벨의 장치와, 고수준의 intelligence가 필요함.  

###### 저수준 레벨의 장치; 메카니즘
기능성을 구현하는데 필요한 저수준 기법을 혹은 프로토콜들   
예시)  문맥교환  
운영체제에게 프로그램 하나를 중단ㄴ하고, 다른 프로그램을 CPU에 할당할수 있게 해주는 것.  
이러한 시분할 메커니즘은 모든 모던 OS들에의해 구현되어있음.  

###### 고수준 레벨의 지능; 정책  
메카니즘 위에 운영체제의 지능이 "정책"이라는 이름으로 올라가있다.  
이러한 "정책"은 알고리즘이다.  
알고리즘은 운영체제가 어떠한 결정을 내릴지를 결정한다.   

예시) 스케쥴링 정책  
OS의 스케쥴링 정책은, 실행 가능한 프로그램들을 받았을 떄, "어떠한 프로그램"을 실행시킬 것인지 결정한다.  
(실행 기록, 자원 사용률 등등 자신만의 기록데이터를 사용하고 기준에 의해서)

### 프로세스 - OS가 제공하는 프로그램에 대한 추상화.  
프로세스는 OS가 프로그램에 대해서 제공하는 추상화 개념이다.  

프로세스는 실행중 프로그램이라고 했음.  
어느시점에든, 우리는 그것이 실행중, 접근하거나 영향을 미치는 목록들로부터 그것을 요약할 수 있음.  


#### 기계 상태 - machine state
프로세스가 무엇으로 구성되는지 이해하려면, 기계상태를 먼저 이해해야함.  

기계 상태란, 프로그램이 실행 중, 읽거나 수정이 가능한 요소들.  
특정 시점에 해당 프로그램의 실행과 관련해 기계의 어떤 부분들이 중요한가?   

가장 명백한 기계 구성은 바로 "메모리"임.  
프로그램의 명령어는 메모리에 위치하고, 프로그램이 읽고 쓰는것또한 메모리에서 한다.  
따라서 프로레스가 접근할 수 있는 메모리(주소공간이라고 부름)는 그 프로세스의 일부임.  

다른 기계 상태의 부분 중, "레지스터"도 있음.  
그중 특수 레지스터
- PC
- stack pointer
- frame pointer

#### 매커니즘과 정책 / 모듈화
주요하게 사용되는 패턴은 매커니즘과 정책의 분리다.  
매커니즘은 How이며, 정책은 which이다.  

즉 매커니즘은, 문맥교환을 어떻게 할것인가? 에 해당.  
어떤 프로그램을 지금당장 실행하는가?(which)에 해당하는 것은 정책이다.  

이렇게 분리하면, 매커니즘을 다시 고민안하고 "정책을 변경" 할 수 있음.  
이런게 설계 원칙인 모듈화의 한 형태임.  

### 프로세스 API / 넘어가면서 보는 시작
나중에 더 자세할거고, 모든 운영체제서 형태는 달라도 주는 개념을 본다.  
- 생성
  - OS는 새 프로세스를 생성하기 위한 것을 가짐.
- 파괴
  - 생성이 있으면 파괴도 있음.
  - 대개 프로세스는 다 끝나면 자동으로 exit하는데 안그러는경우 강제종료는 유용함.  
- 대기
- 기타 제어
  - 파괴 및 대기 이외에도, 유예 같은 기법을 주기도 함.  
- 상태
  - 상태보는거 줌.
 
### 프로세스 생성
1. 반드시 OS는 프로그램의 코드 및 정적 데이터를 메모리에 "로드"해야함. (프로세스의 주소공간)
2. 프로그램은 디스크에 "실행 가능한 포맷"으로 존재함. 따라서 로드라는 과정은 그것들의 바이트를 읽어 메모리의 특정 위치에 배치하는 과정을 포함.

#### 메모리 로드 방식
초기에는 "eagerly" 즉 적극적으로 로드함.  
프로그램을 실행 전에 "모조리" 로드함.  

최근에는 지연적 혹은 게으르게 "lazy" 방식임  
코드 혹은 데이터가 실제 필요할 때만 일부 조각만 로드함.  
-> 좀더 자세하게 이해하려면 "페이징"과 "스와핑"에 대해서 이해해야함.  <- 메모리 가상화 기법임 ^^   


메모리에 정적데이터와 코드를 올렸다면, 프로세스 실행에 조금 더 필요한 개념이 있음.  
### run-time stack (혹은 단순 stack)  
메모리중 일부는 반드시 스택에 할당되어야함.  
C 프로그램을 예시로 스택에 지역변수, 함수 파라미터, return address들을 담는데, 이것을 OS가 메모리에 주고 프로세스에 할당함.  
OS는 또한 스택을 인자로 초기화 할 가능성이 높음 (main  함수의 argc, argv 등의 배열등등)   

#### 힙
또한 힙영역 줄 수 있음. 
C에서는 대개 malloc()으로 받고 free()로 해제함. 힙은 처음에는 작을것이고, malloc()라이브러리 API를 통해서 OS는 점차 더 많은 공간을 할당할 것.  


#### 파일 디스크립터
또한 우영체제는 다른 초기화 작업을 하는데, IO관련된 것임.   
예시로 유닉스에서는 각 프로세스는 3개의 디폴트 파일 디스크립터를 가지는데, 표준 입력 출력 에러이다.   
이런 디스크립터는 프로그램이 터민널로부터 쉽게 입력받고, 쉽게 스크린ㄴ으로 출력수 있게함.  
이건 나중의 영속성 파트에서 배움.  

### 실행
위의 개념들을 처리하고 운영체제는 프로그램 실행 준비를 마침.  
따라서 마지막 하나는 프로그램 진입점인 main()에서 프로그램이 실행되도록 하는 것.  

> "CPU 제어권을 새로 생성된 프로세스에게 넘겨줌으로써 프로그램의 실행이 시작된다"   

### 프로세스 상태 / Process State 
특정 시점에 프로세스가 가질 수 있는 상태  
5가지 혹은 3가지 상태로 구분이 가능하다.  
이때 5가지 상태는 3가지 상태에서 2가지가 추가된 형태이다.  

#### 3가지 프로세스 상태
1. Running - 프로세스가 프로세서에서 돌아가는 상태. 
2. Ready - 특정한 사유(차례가 안옴 등)으로 인해서, OS에 의해서 선택되지는 않았지만, 현재 실행을 위해 대기중인 프로세스 상태.  
3. Blocked - 프로세스가 특정 orperation을 수행한 결과로인해 다른 어떤 "이벤트"가 발생하기 전까지 실행 대기상태가 아닌 상태.

###### 추가 2개 상태
1. 시작
2. 종료

##### 프로세스 상태 변화 이동자
> Scheduled / dispatch
> Ready -> Running
> OS의 "재량"에 의한 이동임.


> Descheduled
> Running -> Ready

> Block
> I/O 요청등에 의해서 I/O요청등이 시작되면 Block으로 이동
> 해당 I/O요청등이 완료되면 다시 Ready로 이동
> OS에 따라서 다르지만, 구현에 따라서 Block -> Ready로 이동하면 곧바로 실행시킬 수도 있음.

### 자료 구조
운영체제 또한 프로그램의 일종이다.  
따라서 운영체제 또한 중요 혹은 관련된 정보 조각들을 관리하기위한 자료구조를 가진다.  

**프로세스 리스트**와 같이 모든 Ready 상태의 프로세스를 관리하는 구조.  
혹은 현재 동작중인 프로세스에 관한 정보.  
혹은 모종의 이유로 block된 프로세스들에 대한 정보 등등.    

##### 문맥 교환 
프로그램은 결국 "레지스터  문맥"이 중요하다.  
프로그램이 프로세스에서 동작하려면 결국 레지스터값이 변화하는 것이기 때문.  

프로세스가 중단되면, 해당 프로세스의 레지스터는 메모리 공간에 저장된다.  
이후 재시작된다면 레지스터 값을 실제 물리 레지스터에 복구시킨다.  
이러한 방식의 기법은 **"문맥 교환"** 으로 부른다.  

###### 시작 상태와 종료 상태
다른 상태들이 존재한다.  
시작상태와 종료상태.   
특히나 종료상태는 대개 부모프로세스와 같은 다른 프로세스가 방금 종료된 해당 프로세스가 성공적으로 종료되었는지 파악 가능하게 한다.  
(유닉스에서는 성공 종료면 0, 아니면 이외)  
프로세스가 종료되면 부모 프로세스는 wait()과 같은 마지막 호출을 수행해, 자식 프로세스의 완료를 기다림.  
운영체제에게 이제 사라진 해당 프로세스와 관련된 데이터 구조들을 정리해도 좋다는 신호를 보낸다.  

#### 중간 정리
프로세스는 동작중인 프로그램.  
프로세스 구현을 위한 저수준 메카니즘.  
프로세스 스케쥴을 위한 지능적 방식을 제공하는 정책.  
이 둘을 조합하는 것으로, OS가 제공하는 CPU 가상화에 대한 이해를 높일 수 있음.

###### fork() System Call
프로세스를 새롭게 생성하는 시스템 콜.  

PID - Process IDentifier  
프로세스 식별자.  

특이점: 아예 새롭게 main()부터 시작시키는 것이 아니라 마치 그 당시의 실행 기록부터 "복제"한것처럼 보임.  

> => 두 프로세스 모두 fork()라는 시스템콜을 반환하려는 상태가 됨.  
> => 자식 프로세스는 자신이 "직접 fork()를 호출 했던것처럼 동작을 이어감"  

부모 프로세스: 새로운 프로세스를 생성한 프로세스.  
> fork()의 결과로 자식프로세스의 PID를 받음.

자식 프로세스: 새롭게 생성된 프로세스.  
> fork()의 결과를 0을 넘겨받음.

> 부모와 자식프로세스의 실행 순서는 "알 수 없음" (결정적이지 않다)    
OS의 입장에서는 단지 "두개의 Ready" 프로세스이기 때문.  
또한 스케쥴러는 복잡하기 때문에, 정확하게 결정론적으로 결과를 확정시키기 힘듬.


###### wait() - System Call
대기하는 함수.  
부모 프로세스가 사용시 자식 프로세스가 실행되고 종료되기 전까지 반환되지 않는다.  
반환 값은 자식 프로세스의 PID값이다.  


###### exec() - System Call
새로운 프로그램을 실행시킬 떄 사용하는 API.  
정확히는 지금 실행중인 프로그램과 다른 프로그램을 실행하는 API이다.  

중요한 특징은.  
> exec()는 새로운 프로세스를 생성하는 것이 아님.  
> 현재 실행중인 프로그램을 다른 프로그램으로 바꿔끼는 것에 가깝다.  
> 대개 fork() 이후, 복사한 자식프로세스에 사용한다.    
> 성공적으로 실행하면 마치 한번도 실행된 적 없던것처럼 된다.  
> 힙 스택 등 메모리공간을 전부 초기화한다. 필요한것은 복사한다.  

성공적으로 수행되면 어떠한 것도 반환하지 않는다.  

###### 왜 사용함?
이 두개의 분리는 유닉스 쉘 구축의 가장 필수적 요소임.  
> 쉘이 fork()이후와 exec()이전 사이에서 code를 실행 가능하도록 해준다.
> 이 code는 새로 실행될 프로그램의 환경을 쉽게 변경 가능하게함
> Shell에서 갖가지 많은 개짓거리를 가능하게 해주는 요소임.  


shell은 동작이 다음과 같음.  

1. 사용자 입력을 기다림
2. 사용자 입력이 들어오면 일반적으로
3. 파일 시스템 내에서 해당 실행파일의 위치를 찾고 fork() 호출
4. 이어서 exec() 계열 함수를 호출 명령을 실행
5. wait()을 호출해 해당 명령이 완료될 떄 까지 대기
6. 자식이 종료되면 wait()에서 반환됨
7. 다시 프롬프트 출력.
8. 다시 입력을 기다림.

추가 예시
> wc 프로그램을 예시로  
> `prompt> wc p3.c > newfile.txt`  
> 라고하면 셀은 자식프로세스가 fork 된 이후, exec 하기 전.  
> 셀(정확히는 자식 프로세스 내부에서 실행되는 코드)는 표준 출력을 닫고 newfile.txt를 연다  
> 이러면 exec로 곧 실행될 wc프로그램은 표준출력이 아닌 해당 파일로 출력됨.  
> "열려 있는 파일 디스크립터는 exec() 이후에도 유지됨" <- 이래서 가능한거

###### 추가적
kill() system call은 프로세스에 "signal"을 준다.  
시그널에는 프로세스 일중단, 종료 그리고 다른 유효환 명령어들이 포함된다.  

사용자 편의를 위해 대부분 유닉스 쉘에 특정 키 조합을 누르면 자동으로 실행중 프로세스에 시그널을 주도록 되어있다.
ctrl c -> 대개 SIGNIT(Interrupt) 신호가 가, 프로세스가 종료됨  
ctrl z -> 대개 SIGTSTP(Stop) 신호가 전달, 실행이 일시 중단 (fg같은걸로 재개 가능)  

모든 Signal 서브시템들은 프로세스에게 외부 이벤트를 전달하기 위한 인프라를 제공한다.  
- 개별 프로세스 ㄴ내부에서의 시그널  수신 및 처리
- 특정 프로세스 혹은 프로세스 그룹 전체로 시그널을 전송하는 방법 등.

사용하려면 프로세스는 signal() 시스템 호출을 통해 다양한 시그널을 catch 해야만함.  
-> 특정 프로세스에, 특정 시그널 도착시, 해당 프로세스느 정상 실행 흐름을 중단.  
-> 시그널에 대응하는 특정 코드를 실행.  

> 유의사항    
> 리눅스 쉘이서, kill은 프로세스 종료용이 아닌 "signal"을 보내는 용도이다.  
> 다만 별도 옵션등을 안주고 사용하면 기본값이 프로세스 종료 signal을 보내는 것이다.

### 매커니즘 - 제한된 직접 수행
시분할 방식으로 CPU 가상화 시 다음과 같은 두개의 문제가 발생한다.  
1. 퍼포먼스 - 최대한 오버헤드가 적게
2. 제어 - CPU에 대한 제어권을 유지하면서도, 어떻게 효율적으로 실행하냐.  

해결법
##### 제한된 직접 수행

###### 직접 수행
단순  
해당 프로세스가 CPU 자체를 직접 차지하여 동작함.  

OS는
- 프로세스 항목 생성
- 메모리 할당
- 메모리 적재
- 진입전 찾기
- 해당 진입점으로 jump (main()을 실행) ( execute call main())
  - run main()
  - execute return from main
- 종료된 프로그램의 메모리 할당 해제, 프로그램 리스트에서 제거

여기서 "직접 수행"의 문제점.  
1. 운영체제는 어떻게 프로그램이 원치 않는 동작을 "제어" 하냐  
2. 동작중인 프로세스는 CPU를 점유중인데, OS가 어떻게 해당 프로세스를 멈추고 시분할을 구현하나?

> 왜 "제한된" 이 붙는지 명심할 것.

#### Restricted Operations
프로세스가 CPU를 독점해 동작해서 빠르고 효율적이긴하다.  
근데 어떻게 금지된 동작을 막을까?  , I/O 입출력 요구, 혹은 시스템 자원에 대한 접근 혹은 획득(CPU, Memory 등)  

---

`open(), read()`와 같은 시스템 콜이 왜 C언어의 프로시저같아보일까?  
실제로 프로시저임 ㅇㅇ.  
다만 해당 프로시저 내부에서 "trap" 명령어가 숨겨져 있음 
정확히는 `open()` 호출할 때, C라이브러리 내부로 드렁간는ㄴ 프로시저 호출을 실행하고 있는 것.  

그러면 open이건 read등이거 아무튼 라이브러리는 커널과 사전에 합의한 호출규약을 준수함.  
-> 프로시저 open()의 인자들을 잘 알려진 위치에 배치, 시스템콜 번호 역시 넣고 언급한 트랩 명령어를 실행함.  
-> 이후 라이브러리 코든는 반환값을 풀어서 정리, 시스템 콜을 발생시킨 프로그램으로 제어권 반환.  

---

그냥 내버려두면 안되므로, 사용자모드와 커널모드를 도입하는 것.

사용자모드  
> 실행할 수 있는 작업에 제한이 존재함.  
> I/O, 자원 접근등에 "직접 수행"이 불가능  
> 하려고하면 예외 발생함  

커널모드  
> 입출력 수행  
> 제한된 명령어등 모든 동작 가능.  

시스템 콜  
> 사용자 모드의 프로세스가 특권 작업을 수행하고자 할때 호출하는 것.  

트랩 명령어  
> 시스템 호출을 실행하기 위한 특별한 명령어
> 커널로 제어를 이동시키는 동시에 권한 수준을 커널 모드로 격상.


작업 와료시 운영체제는 특별한 트랩 복귀 명령어(return-from-trap)를 수행  
> 제어를 다시 호출한 사용자 프로그램으로 되돌려보냄.
> 권한 수준을 다시 사용자 모드로 낮춤.

트랩시 어떤 코드를 실행할 지, 즉 OS의 어느 부분으로 점프할지는 호출하는 쪽이 지정하면 안됨.  
커널은 트램 발생시 어떠하 코드가 실행될지를 엄격하게 제어해야함.  

커널은 부팅 시점에 트랩테이블(trap table)을 설정.  
시스템 부팅시에는 커널모드로 동작.  자유로운 하드웨어 구성 가능.  

운영체제는 보통 일종의 특수 명령어 사용해 하드웨어에 이러한 트랩 핸들러의 위치를 알려줌.  
정보 한번 받으면 재부팅 전까지 기억.  

시스템 호출 과정에서 운영체제를 보호하기위해 하드웨어 트랩 메커니즘을 도입, 모든 운영체제 호출이 반드시 이 메커니즘을 거치도록.  
많은 노력 기울였어도 고려해야할 요소는 많다.  대개 인자 처리 방식등에서 조심해야함.  

또한 대개 특정 시스템호출을 명시하기 위해서는, "대표되는 시스템 호출 번호"가 할당됨.  
직접 점프 주소를 정하는게 아니라, 호출시 해당 번호를 제공하고  
운영체제는 유효성을 검증한뒤 코드를 실행하는 것으로 일종의 보호 수단으로 작용하기도 함.  

#### 제한적 직접 수행 (LDE)의 단계
대개 2단계로 구성

###### 1단계
부팅단계  
커널이 특권 명령어를 사용해 작업을 수행.  
커널이 트랩테이블을 초기화, CPU는 이 테이블ㅇ위치를 기억함. 

###### 2단계  
프로세스 실행 시
커널이   
- 프로세스 리스트에 노드 할당
- 메모리 할당
- 메모리에 적재 등

을 수행한 후 return-from-trap 명령어를 통해, 프로세스 실행을 시작함.  
CPU는 사용자 모드로 전환됨.  
프로세스가 실행됨.  

이후는 이전의 설명처럼 트랩을 통해 요청하고 반환받는것을 하다.  
프로세스가 종료되려면 보통 stub 코드라는 운영체제가 프로그램이 적절히 종료될 수 있도록 돕는 코드로 이어짐.  
(exit() 시스템 호출로 운영체제로 트랩을 방생시키는 방식 등이 여기에 해당)  
이시점에는 운영체제가 필요한 정리작업을 수행해줌.   

---

#### 프로세스 스위칭  
프로세스 전환을 어떻게 구현하냐..   
운영체제는 제한된 직접수행에 의해 CPU에 존재하지 않는 상태인데 어떻게 프로세스를 스위칭한다는 "수행"을 하냐?  

> 제어 권한을 어떻게 다시 받냐 이말이다.

##### 1. 협력적 접
모든 프로세스가 합리적이라고 생각한 경우.  

- 양보를 위한 시스템 호출
- 혹은
- 0으로 나누기, 권한 없는 접근 등등의 trap 발생 요소

즉, 운영체제는 양보를 명시적으로 받거나, 혹은 잘못된 동작이 일어나기 까지
> 기다려야함.

-> 안주면? -> 걍 재부팅해야지. ㅇㅇ .  


##### 2. 비 협력적 접근
위와같은 비 협적적 상황에 대비하기 위함.  
timer innterrupt (인터럽트) 개념을 도입.  
일정 주기(ms; 밀리초)마다 인터럽트를 발생시킬 수 있음.  

인터럽트 발생 -> running process stop -> os' interrupt handler work   
-> OS의 제어권 획득.  

또한 하드웨어도 인터럽트 발생시 실행중이던 프로세스의 상태를 충분히 저장해야함.  
-> return-from-trap 명령어가 실행될 떄, 해당 프로그램을 올바르게 재개 할 수 있음.  

명시적이 시스템 호출을 통해 커널로 진입할떄, 하드웨어가 보이는 동작과 매우 유사.  
즉, 여러 레지스터가 커널 스택등에 저장되고, 이후 return-from-trap 명령어를 통해 쉽게 복원 될 수 있는것.

###  문맥을 저장하고 복구시키는 것.  
일단 어떻게 프로세스를 전환할지는 스케쥴링 정책인데,   

> 프로세스를 전환하기로 했으면 문맥 교환이라는 저수주 코드를 실행함.

##### 문맥 교환

> 현재 실행중 프로세스의 레지스터를 저장
> 다음 실행할 프로세스의 레지스터를 복원

-> return-from-trap 명령이 실행 될 떄, 이전 프로세스를 돌아가는 대신, 다른 프로세스 실행을 재개할 수 있도록 보장.  

현재 실행중 프로세스 문맥 저장을 위해  
- 현재 실행중 프로세스의 여러 레지스터
- 및 커널 스택 포인터를 저장하는 저수준 어셈블리 코드 실행
- 이후 실행될 프로세스의 레지스터들과 PC 복원, 커널 스택을 전환

-> 스택을 전환한다 -> 커널은 중단될 한 프로세스의 문맥에서, 전환코드 호출로 진입했다,  다른프로세스의 무맥에서 리턴하게 됨.  
-> 이후 OS가 return-from-trap 명령을 실행하면, 곧 실행 될 예정이었던 프로세스는  
-> 현재 실행중인 프로세스가 됨.  
-> 문맥 교환 종료  

##### 주의점
타이머 인터럽트시

먼저 하드웨어에서 프로세스의 레지스터(유저 모드 문맥) 를 해당 프로세스의 커널스택에 저장  
이후 커널모드로 변경  
이후 트랩 핸들러로 점프  

그다음  

커널모드에서는  (OS)  
프로세스를 변경하기로 결정  
커널코드의 문맥을 저장.  
저장 위치는 struct proc의 context 필드(프로세스 구조체)  
이후 반대로 다른 프로세스의 구조체에서 커널 영역의 레지스터 복구
다른 프로세스 스택으로 전환.  

그다음  하드웨어에서 위위걸 반대로 실행.

### 스케쥴링
프로세스의 실행에 관한 "저수준 매커니즘"은 위에서 봄.  
이제 스케쥴러가 사용하는 고수준의 지능적 "정책"은 모른다.  

스케쥴링 정책은 disciplines 라고도 함.  

스케쥴링 정책 수립시  
> 기본 특, 핵심 가정, 중요한 지표, 접근 방식

워크로드  
> 시스템 내에서 실행되는 프로세스들을 통칭하는 말.
> 워크로드 파악은 정책 수립의 중요 단계
> 잘 알아야지 정교한 정책이 가능.
> 행하면서 이러한 가정들을 점차 완화해 나갈 것이며, 최종적으로는 '완전히 작동 가능한 스케줄링 방식(fully-operational scheduling discipline)'이라 부를 수 있는 체계를 구축

프로세스는 일종의 job이라고도 표현하기도 함.
