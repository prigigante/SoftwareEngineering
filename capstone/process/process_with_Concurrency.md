# 시작하며
이전에는 기본적인 추상화 기법을 배웠다.  

프로세스란 CPU를 가상화하여 "하나의 CPU를" 가상 CPU여러개를 사용하는 것처럼 보일수 있는지 알았다.  
이러한 기법은 여러개의 프로그램을 동시에 실행하고 있는것같은 "착각"을 가능하게 했다.  
또한 우리는 각 프로세스에 대해 크고 독립적인 가상 메모리라는 환상을 어떻게 만들어내는지 살펴보았습니다.  
이러한 주소 공간 추상화를 통해 각 프로그램은 마치 자신만의 메모리를 가진 것처럼 동작할 수 있는데,   
실제로는 운영체제가 물리적 메모리(때로는 디스크까지 포함하여) 전반에 걸쳐 주소 공간들을 은밀하게 다중화(multiplexing)하고 있는 것입니다.

## 주요 점
새로운 추상화를 소개한다.  
"하나의 단일 실행 프로세스" 를 위한 가상화다.  
부르기를
#### Thread

기존의 우리가 단하나의 실행 지점 (하나의 PC)만 생각했다면,    
multi-threaded 프로그램은 더 많은 실행 지점을 가진다(여러개의 PC)  

따라서 각각의 스레드들은 개별 프로세스와 매우 유사하다.  
다만 중요한 하나가 다르다.  
> 프로세스들은 같은 주소 공간을 "공유"하기 때문에, 각각 서로 같은 데이터에 접근이 가능하다.

따라서 일단, 싱글 스레드의 상태는 프로세스와 굉장히 유사하다.  
스레드 또한 PC를 가진다.  
각각의 스레드는 연산을 위해 각각의 개별 레지스터 세트를 가진다.  
따라서, 만일

> 단일 프로세서에서
> 돌아가고 있는 스레드T1에서
> 다른 스레드T2로 스위칭하려고 할때
> 문맥 교환은 반드시 필요하다.

스레드간 문맥교환은 프로세스간 문맥교환과 굉장히 유사하다.  
T1의 레지스터 상태는 반드시 저장되어야한다.  
T2의 레지스터 상태는 반드시 복구되어야한다.  

프로세스 상태는 PCB(Process Control Block)에 저장했다.  
따라서 우리는 프로세스의 각 스레드들을 저장하기 위해  
하나 혹은 그  이상의 Thread Control BLocks(TCBs)가 필요하다.    
단 주요 차이점은 다음과 같다.  
> 동일한 주소공간을 사용하기 때문에  
> 사용할 페이지 테이블을 교체할 필요가 없다.   

또다른 차이점
스택에 있어서 차이점이 존재한다.  
다중 스레드 프로세스에서는  스레드는 독립적으로 실행되며,  당연히 자신의 작업을 처리하기위해 여러 루틴호출이 가능하다.  
따라서 스레드당 하나의 스택을 둔다.  


스택에 할당되는 변수, 매개변수, 반환값 등은 '스레드 로컬 저장소(thread-local storage)',   
즉 해당 스레드의 스택에 위치하게 됩니다.  
이로 인해 기존의 깔끔했던 주소 공간 레이아웃이 흐트러진다는 점도 눈치채셨을 겁니다.   
이전에는 스택과 힙이 독립적으로 확장될 수 있었고, 주소 공간이 부족해질 때만 문제가 발생했습니다.   
하지만 이제는 상황이 더 이상 그렇게 이상적이지 않습니다.   
다행히도 스택은 일반적으로 매우 클 필요가 없기 때문에(재귀를 많이 사용하는 프로그램은 예외입니다), 보통은 큰 문제가 되지 않습니다.  

### 왜 스레드 씀?  
주요한 2가지 이유로 인해서 스레드를 사용한다.  

#### 1. parallelism
병렬성때문.  
아주 큰 배열 대상으로 더하거나 증가시키는 연산 상상.  
단일 프로세서에서 실행하면 작업은 단순하게 차례대로 연산을 수행하고 끝낸다.  

다중 프로세서 시스템에서 수행하면 각 작업을 나누어 상당히 가속이 가능함.  
표준적인 단일 스레드 프로그램을 이처럼 여러 CPU에서 분담하도록 변환 하는 개념을
> parallelization 이라고함.

CPU 하나당 하나의 스레드 사용. 이작업을 수행하는 것은 현대 하드웨어에서 프로그램을 더 빨리 실행하도록하는 대표 기법.  




#### 2. 느린 I/O로 인해 프로그램이 차단(Block) 되는것을 막고자
다양한 유형의 I/O를 수행하는 프로그램을 작성한다 가정  

I/O 작업과 관련해, 명시적 디스크 IO가 끝나거나 혹은 암묵적으로 페이지 폴트 처리가 끝날떄가지 기다릴 수 있음.  
이 경우 무작적 기다리는 것은 손해가 너무 큼  
-> CPU를 활용해 연산을 수행하거나 추가적인 I/O요청을 발행하는 작업을 수행 가능.  

스레드 사용은 Stuck이라는 프로그램이 멈추는 현상을 피할수 있는 방법.  
I/O등으로 프로그램의 한 스레드가 대기중일 때  
CPU 스케쥴러는  
실행 가능한 유용한 작업이 가능한 다른 스레드로 전환 가능  

멀티 프로그래밍이 프로그램들 간 프로세스를 통해 그렇게 한 것처럼, 
"스레딩"은 "단일 프로그램" 내부에서 "I/O와 다른작업의 중첩"이 가능하게 함.  
현대의 수많은 서버 기반 애플리케이션(웹 서버, 데이터베이스 관리 시스템 등)은 구현 시 스레드를 적극적으로 활용하고 있습니다.  

스레드 대신 여러 프로세스를 사용할 수도 있습니다.  
하지만 스레드는 주소 공간을 공유하므로 데이터를 공유하기가 쉽고,   
따라서 이러한 유형의 프로그램을 구축할 때 자연스러운 선택지가 됩니다.  
반면, 메모리 내 데이터 구조를 거의 공유할 필요가 없는   
논리적으로 독립적인 작업의 경우에는 프로세스를 사용하는 것이 더 합리적인 선택입니다.

### 스레드 생성
스레드 두개를 추가로 하나의 프로세스에서 생성한다고 했을 때, A와 B라고 한다면,  
같은 함수를 실행하도록 하지만, 다른 인자를 준다고 가정   

스레드는 생성되자마자 실행 될 수도, 혹은 그냥 ready 상태로 들어갈 수 도 있다.  

`pthread_join()`으로 스레드 종료를 기다릴 수 있다.  
이를 활용한 예시를 통해서 우리는,  스레드 실행을 예측할수 없다는것을 볼수있다.  
스레드 실행은 마치 함수 실행과 같아보이지만,  
일반적인 함수는 함수를 먼저 실행한 뒤 호출자로 돌아오지만,  
스레드 생성은, 시스템이 호출된 루틴을 위해 새로운 스레드를 생성한다는 점,  


새로운 스레드는 호출자와 독립적으로 실행되는데,  이로인해  
스레드 생성 함수가 반환 되기도 전에 실행될 수도 있고,  
혹은 한참 뒤에 실행될 수 도있다.   

뭘 먼저 실행할지는 스케쥴러가 결정하는데, 스케쥴러를 예측하는것은 매우 힘들다.    

예시를 통해서,  우리는 스레드가 굉장히 복잡하게 만든다는것을 알 수 있다.  
애초에 이미, 무엇이 언제 실행된다고 말하기 힘든 상황인데,   
동시성 없어도 이해힘든데,  
여기에 동시성(concurrency)까지 추가되면 더힘들다.

#### 공유 데이터의 문제점
스레드 두개를 만드는 코드에서  
1. 단순하게 두개 생성하게 함
2. 워크 스레드를 위해 두개의 별도 함수본체말고, 하나의 코드조각만 사용하고 스레드에 인자를 전달해 출력하도록 함.
3. 내용은 전역변수를 더하는 것
4. 기대값은 2천만

> 결과: 무작위적.  
> 어떠한 것도 잘못된것이 없지만, "결과는 전부 무작위적이다"

#### 왜 이지랄이 나는지: 제어불가능한 스케쥴링
예시를 든다.  
우리가 기대하는게 총 50부터 시작해서 각 스레드 하나씩 총두개로  
1씩 더하여  
50 + 1 + 1 = 52 를 기대하는 프로그램이 있다고 가정하자.  
x86등의 레지스터 연산에 의해서 보다보면   


###### 스레드 1에서
eax까지만 51이 되고, 메모리(전역변수)에 저장하지 못하고 스위칭이 일어나고  

###### 스레드 2에서
이놈은 메모리(전역변수)에서 "50"을 꺼내서  
연산 후, 메모리(전역변수)에 성공적으로 "51"을 저장했다.  

왜냐? 스레드1 과 스레드2는 독립적인 레지스터를 가진다고 여겨지기 때문.  
레지스터는 문맥 교환에 의해 추상화 되어, 저장되고 복구된다.  

###### 다시 스레드 1에서
이놈은 이전 레지스터를 복구해 다시 eax가 51이 되고,  
이 값을 메모리에 "저장" 한다.  

###### 결과
결과적으로 기대값은 52였지만,  
실제적으로는 51이 저장되었다.   

이러한 설명에 부합하는것이 바로  
#### Race condition; 경쟁 상태
위 경우 좀더 구체적으로는 data race  

이러한 결과는 우리가 보통 보던 깔끔한 결정론적 연산이 아닌, 비결정론적 하다고 부른다.  
이는 어떤 결과가 나올지 알 수 없고, 매 실행마다 결과가 다를 가능성이 높다.  

이코드를 실행하는 여러 스레드로 인해, 경쟁상태가 발생할 수 있다.  
따라서 우리는 이런 코드를 critical section(임계 구역)이라고 부른다.  
임계 구역이란 공유변수(일반적으로는 공유 자원)에 접근하는 코드의 일부분을 의미  
> 둘 이상의 스레드가 동시에 실행해서는 안되는 영역

이러한 코드에서 원하는건 mutual exclusion(상호 배제)이다.  
이 속성은 하나의 스레드가 임계구역에서 실행 중인 경우,  
다른 스레드는 그러지 못하게 **"보장"**해준다.

### The Wish For Atomicity
우리가 원하는건 원자적 실행을 보장하는 것.  
덧셈 연산시의 3가지의 instruction 순서를 "원자적이게" 실행하는 것.  

###### 문제점
아까 단 하나의 전용 instruction이면 해결된다고 했자늠?  

따라서,  동시적으로 B-tree를 작성한다고 해보자.  
그리고 이것을 업데이트 하려고하는데,  이떄 하드웨어한테  
> Q: 야 B-tree 용으로 전용 atomic update instruction 내놔
>
> A: 미쳤냐?



###### 방법
하드웨어의 도움을 받아, 하드웨어에서 synchronization primitives(동기화 기본요소?)라는 유용한 instructions 를 요청한다..  
또한 이것과 운영체제의 도움을 받는다면, 임계구역에 동기화되고도 제어되는 방식으로 접근하는 
멀티스레드 코드를 작성 가능하다.  
-> 동시성 실행이 수반하는 복잡하고 까다로운 상황속에서도, 항상 정확한 결과를 신뢰성있게 도출 가능.

### 또 하나의 문제점; Waiting For Another
이 장에서는 동시성 문제를 다룰 때, 마치 스레드 간 상호작용이 '공유 변수에 접근하는 것'과 '임계 구역(critical section)에 대해 원자성(atomicity)을 보장하는 것'이라는 한 가지 유형으로만 존재하는 것처럼 설정했다. 하지만 실제로는 또 다른 흔한 상호작용 유형이 존재한다. 바로 한 스레드가 다른 스레드의 특정 작업이 완료될 때까지 기다려야 하는 경우이다. 이러한 상호작용은 예를 들어, 프로세스가 디스크 I/O를 수행하다가 대기 상태(sleep)로 전환되는 상황에서 발생한다. 이후 I/O 작업이 완료되면, 해당 프로세스는 다시 깨어나 작업을 이어갈 수 있어야 한다.  
따라서 이어지는 장들에서는 원자성(atomicity)을 보장하기 위한 동기화 기본 요소(synchronization primitives)를 구현하는 방법뿐만 아니라, 멀티스레드 프로그램에서 흔히 나타나는 '잠들기/깨어나기(sleeping/waking)' 상호작용을 지원하기 위한 메커니즘에 대해서도 살펴볼 것입니다. 지금 당장 이 내용이 잘 이해되지 않더라도 괜찮습니다! '조건 변수(condition variables)'를 다루는 장을 읽어보면 곧 자연스럽게 이해될 것입니다. 만약 그때가 되어도 여전히 이해되지 않는다면, 그건 조금 곤란한 상황이니, 완전히 이해될 때까지 해당 장을 반복해서 다시 읽어보시기 바랍니다.  

주요한 용어  
- Critical Sectionn
- Race Condition
- Inndeterminate
- Mutual Exclusion
